# Contributing

Issues and pull requests are welcome. This file covers setup, tests, and what a pull request should look like. It also describes the optional house commit-message rules in `githooks/`, which are for the maintainer and not required for contributors.

## Development setup

You need Python 3.11 or newer and git. Shuin has no runtime dependencies, and `pytest` is the only development dependency.

```bash
git clone https://github.com/tflaim/shuin.git
cd shuin
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
```

Activate the virtualenv (`. .venv/bin/activate`) or call `.venv/bin/python` directly in the commands below.

## Running the tests

```bash
python -m pytest
sh githooks/test.sh
```

Both commands should finish with no failures. The hook tests run real git commands in a temporary repository and need `git`, `awk`, `mktemp`, and `sed`. They also need `perl`: three of the tests use it to start the hook in its own process group, and without it those three fail. The hooks themselves do not use perl.

No formatter or linter is configured. Match the surrounding code.

## Pull requests

- Keep the diff small and focused on one change.
- Add or update tests under `tests/` that assert behavior, meaning what a user or caller can observe, not how the code is arranged inside.
- Run `python -m pytest` before you open the pull request.
- Keep the project free of runtime dependencies.
- No GitHub Actions are used, so the tests run on your machine. Say in the pull request what you ran.

Do not report security problems in a public issue or pull request. See [SECURITY.md](SECURITY.md).

By contributing you agree that your work is released under the MIT license.

## House commit-message rules (opt-in)

`githooks/` holds the maintainer's own commit-message rules, as two git hooks. They are opt-in and not required for contributors: cloning the repository does not enable them, and you can open a pull request without them. The maintainer turns them on in a clone with:

```bash
git config core.hooksPath githooks
```

There is no separate installer; that one setting is the whole installation. If you enable them in your own clone, they will reject your commits and pushes, because the author identity and branch names are fixed to the maintainer's.

What they do:

- `githooks/commit-msg` rejects a commit unless both the author and the committer are exactly `Thomas Flaim <tflaim@gmail.com>`. The error prints the `git config` commands that fix the name and email.
- `githooks/commit-msg` also applies a trailer policy to the commit message. A `Co-authored-by`, `Coauthored-by`, `Co_authored_by`, `Generated-by`, or `Made-with` line is rejected whatever its value. The trailers `Assisted-by`, `Reviewed-by`, `Signed-off-by`, `Co-developed-by`, `Suggested-by`, and `Tested-by` are rejected only when the value names a tool or vendor from the list in `githooks/attribution.sh`. A "Generated by" or "Generated with" footer naming one of those tools is rejected, as are a few link and marker patterns, which are also in that file. The hook first drops the diff that `git commit -v` appends and the comment lines, and it normalizes invisible characters and quote markers before it matches.
- `githooks/pre-push` allows pushes only to branches named `tflaim/<slug>`, where the slug starts with a lowercase letter or digit, and to tags. It refuses pushes to `main` or `master`, and refuses any other branch name. Deleting a branch other than `main` or `master` is not blocked.
- `githooks/pre-push` also checks every commit it is about to push that is not already on the remote's `main`. It applies the same author, committer, and trailer rules to them, which catches commits made with `--no-verify`. It checks annotated tag messages against the trailer rules too.
- `githooks/attribution.sh` holds the shared patterns and temp-file helpers that the two hooks load. It is not a hook itself.
- `githooks/test.sh` is the test suite for the hooks above.
